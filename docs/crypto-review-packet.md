This packet is intended for external academic or professional review of the
cryptographic foundations of TorusDB. It covers the no-key delegation protocol
Π, the SPDZ-style MAC for integrity, and the Laurent Series Secret Sharing
scheme for key custody.

---

## 1. System Overview

TorusDB is an encrypted SQL database where **the server holds no key material
and performs no decryption**. All keys and masks live exclusively on the client
(data owner). The server operates over blinded scalars in Z/nZ.

**Information-theoretic bound (Theorem 30, Lee 2026):**

> For any adversarial server S* and any two plaintexts m, m',
> the statistical distance Δ(V_S(m), V_S(m')) = 0.

That is, the mutual information I(M; V_S) = 0 — the server's view is
information-theoretically independent of the plaintext, unconditionally.
This holds even against computationally unbounded adversaries and is
post-quantum by definition.

## 2. Encoding Layer

**Claim (Rational Reconstruction, §III):**
The encoding ring Z/nZ with n = 2^254 + 10 (the BN254 scalar field order)
supports exact rational reconstruction for all values |p/q| < B where B is
a system-specific bound satisfying B^2 ≪ n/4 (Howgrave-Graham bound).

**Implementation:** `core/torusdb_core/protocol.py`, functions `encode`/`decode`.

**Verification:** The test `test_rational_encode_decode` (`core/tests/test_nokey.py`)
round-trips a set of rationals including edge cases (denominator > 1,
negative values, large magnitude) and verifies exact reconstruction.

**Review question:** Is the bound B = floor(n^(1/4)) a safe choice, or is a
smaller bound needed to prevent reconstruction ambiguity in aggregate
contexts (where sums up to N×B are decoded)?

## 3. Protocol Π — No-Key Delegation

### 3.1 Π_lin (Construction 16): Affine Aggregation

**One-time pad blinding (§VI, Construction 14):**

For each scalar s (an encoded plaintext cell), the client samples a fresh
uniform mask r ← Z/nZ and stores the blinded value ṽ = s + r (mod n) on
the server. The mask r is kept in the owner's mask vault.

**Claim:** The server's view ṽ is uniformly distributed over Z/nZ regardless
of s. Proof: r is uniform, so ṽ = s + r is a one-time pad.

**Aggregation (Construction 16, step 2):**

For a SUM query over rows {i₁, …, iₖ}:
- Server computes: Σ ṽᵢ (mod n) = Σ(sᵢ + rᵢ) = Σsᵢ + Σrᵢ (mod n)
- Client computes: Σrᵢ from vault, reconstructs Σsᵢ = (server result − Σrᵢ) mod n
- Client decodes: decode(Σsᵢ) = exact sum of plaintexts

**Non-interactive:** No round trip beyond the single query RPC.

**Implementation:** `NoKeyServer.blinded_sum`, `NoKeyClient._pi_lin_sum`
in `core/torusdb_core/nokey_engine.py`.

**Verification test:** `test_nokey_sum_correct` — verifies SUM of 3 values.

### 3.2 Π_mult (Construction 18): Beaver-Triple Product

**Pre-condition:** Column policy = PAIRED (both sides stored blinded in Z/nZ).

**Protocol (one round per pair of rows, batched):**
1. Client generates a fresh Beaver triple (a, b, c) with c = a·b mod n.
2. Client reads operands sl, sr from vault (unblinding locally via
   `_read_verified_scalar`).
3. Client computes openings: e = sl − a, g = sr − b (mod n) and sends to server.
4. Server computes: e·g mod n (the "combined opening") and returns.
5. Client reconstructs: sl·sr = c + g·sl + e·sr − e·g (one modular evaluation).

**Claim:** The server learns only e = sl−a and g = sr−b, which are uniformly
distributed (a, b are fresh per triple). It cannot recover sl or sr.

**Implementation:** `NoKeyClient._pi_mult_products` and
`NoKeyServer.mult_combine_batch`.

**Verification tests:**
- `test_nokey_dot_correct` — DOT(a,b) = Σaᵢ·bᵢ for 3 row pairs.
- `test_nokey_pi_mult_depth1_circuit` — evaluates (x1·x2+x3)·x4+x5 using
  two rounds of Π_mult, verifying depth-2 correctness.
- `test_server_has_no_keys` — structural: asserts no `key`, `mask`, `r`,
  `secret` attributes on NoKeyServer instance.

**What the server actually contributes (read this, reviewers).** In this
implementation the owner reconstructs the operand scalars s, s′ (it holds the
masks) before opening them against a triple, and the server's step `e·g` is a
product of two numbers the owner already knows. Π_mult therefore preserves the
*server-view* guarantee (e, g are uniform) but does **not** offload work: DOT
and `a * b` cost O(n) owner bandwidth and computation. We keep the round trip
only because it exercises the MAC check `eg == e·g`. See finding F-3 in §11.

**Review question:** The Beaver triple is generated client-side (single party).
For the single-owner deployment modeled here, is this secure? For multi-owner
deployments, Beaver triples must be generated by an MPC protocol
(e.g., SPDZ preprocessing). This is noted in the threat model but not yet
implemented.

### 3.3 Π_C for SQL expressions (dialect v0.6): secret-shared wires

**Implementation.** Server half: `core/torusdb_core/wires.py` (`WireStore`; RPCs `wire_exec`,
`wire_free`; `server/nokey_server.py::Engine._wire_rpc`). Owner half:
`core/torusdb_core/expr_shared.py` (`SharedExprRunner`; the module docstring is the authoritative
"who computes what"). Planner node `PExpr` (`planner.py`); the static rules shared with the open
validator are in `parser/torussql_parser/expr.py` (`analyze_expr`). Wire format:
`proto/torussql-wire-v2.md` §9. The previous owner-computed evaluator is kept as
`expr_mode="owner"` (`expr_eval.py`) and described at the end of this section.

**Model.** Every wire `X` of the circuit is a two-party additive sharing over `Z/nZ`:
`X = X_S + X_O`. A stored cell `x̃ = x + r` is the wire with `X_S = x̃`, `X_O = −r` (the mask is
already in the owner's vault, so loading a wire sends nothing but row ids). Public values
(literals, plain columns) have `X_S = v`, `X_O = 0`. In authenticated mode a wire also carries
shares of its SPDZ tag `α·X`; a stored MAC cell `m̃ = α·x + r_m` loads as the tag wire.

| Step | Server computes (its shares only) | Owner computes (its shares only) | Messages |
|---|---|---|---|
| load a column | `X_S = x̃` (reads its own stored cells) | `X_O = −r` from the vault; **no cell is fetched** | row ids |
| `+ − neg`, × public, ÷ public, `SUM`, `AVG`, broadcast | the operation on `X_S` | the operation on `X_O` (`+c`: server only; tag: owner adds `α·c`) | none (rides on the next level's request) |
| linear `SUM(Σκ·col)` | `Σ x̃ᵢ` per column (`loadsum`) | `−Σ rᵢ` (`maskstore.sum`) | batch |
| product `Z = X·Y`, level ℓ | `e_S = X_S−u_S`, `g_S = Y_S−v_S`; with `e = e_S+e_O`, `g = g_S+g_O`: `Z_S = w_S + e·v_S + g·u_S + e·g`, **stored as a new wire**; returns `(e_S, g_S)` (+ tag shares) | per product element: a fresh triple `(u,v,w=uv)`, additively shared, server gets `(u_S, v_S, w_S)` only; sends `e_O = X_O−u_O`, `g_O = Y_O−v_O`; learns `e, g`; `Z_O = w_O + e·v_O + g·u_O`; auth: checks the tags of `e`, `g` | **one request/response per level**, batched over all rows and all products of the level |
| `x / y`, `y` encrypted | `[ρ]·[y]` as a product; later `ρ_S · t⁻¹` | deals uniform **non-zero** `ρ` as a sharing (`put`); reads `t = ρ·y` (from the server's share of the product in the same response), MAC-checks it, replaces `t = 0` by a fresh non-zero dummy, sends `t⁻¹` as a public multiplier (`mulv`); `ρ_O·t⁻¹` | `t` is opened inside the product's request; `x/y` is then one more product level |
| result | sends its share of the result wire (`reveal`) | `Z_S + Z_O`; MAC check; strict decode (`OutOfBudget`); `DivisionByZero` only after the last request | the server never receives the result |

`mult_rounds` = product levels = `depth` + one per sequential division by an encrypted value; the
query exchanges `mult_rounds + 1` requests (`last_expr_cost["requests"]`). Cost accounting
(`last_expr_cost`): `mode, depth, mult_rounds, products, inversions, linear_sums, openings, wires,
requests, reveals`. Measured in-process on one core (server work included), 3 000 rows,
`SUM(a*b*c*d)`: owner mode 0.06 s, shared 0.15 s (0.32 s authenticated) — **this mode is not faster;
the owner still does O(rows) ring arithmetic per level on its shares** (a triple and an opening per
product element). That work is inherent to unconditionally secure two-party computation. What changed
is where the intermediates live and what the owner's code does: it fetches no operand cell
(`tests/test_expr_shared*.py` assert that no `blinded_cell(s)`/`mult_combine_batch` RPC is used and
that only the result is decoded), unmasks nothing, and forms no product or quotient in plaintext.

Communication per product element: 5 ring elements to the server (`u_S, v_S, w_S, e_O, g_O`) and 2 back
(`e_S, g_S`); with tags 8 and 4 - about 3.5x (6x) the paper's two openings, because the server's triple
shares are shipped rather than derived. Deriving `(u_S, v_S, w_S)` from a short seed would remove three
(six) of them without weakening the argument below (secrecy needs the server's shares only to be
independent of the data); not done.

**What each party learns.**

* **Server.** The expression shape (levels, products per level, row count, which rows) and a
  view that is uniform and independent of the data: stored cells `x̃`; its triple shares
  `(u_S, v_S, w_S)`; the owner's opening shares `e_O, g_O`; the sharing `ρ_S`; the multiplier `t⁻¹`;
  public constants of the query. It computes `e, g` (uniform) and `t` (uniform on non-zero values).
  It learns neither a product nor the result.
* **Owner — the weak point, read carefully.** The owner is the *dealer*: it knows `(u, v, w)` and `ρ`.
  The openings `e = X−u`, `g = Y−v` and `t = ρ·y` are public to both parties, so
  `X = e + u`, `Y = g + v` and `y = t/ρ` are computable from the owner's own view. The
  implementation never computes them (verified by the tests above) but this is a property of the code,
  **not a cryptographic guarantee against a curious owner**: with one party being both dealer and
  data owner, "nobody reconstructs an intermediate" holds against the server (unconditionally) and for
  an honest owner process, but not against the owner as an adversary. In the single-owner model this
  leaks nothing the owner does not already hold; for multi-owner use (F-9) or an owner that must not
  see intermediates one needs triples that no party knows — a third non-colluding dealer, or
  computational OT/HE-based triple generation between owner and server — which breaks the
  unconditional claim or adds a party, and is **not implemented** (F-22). This corrects the
  requirement that the owner "never reconstructs any operand or intermediate": that is not achievable
  with an owner-dealt Beaver triple.

**Why `t = ρ·y` reveals nothing to the server.** `ρ` is uniform on `Z*_n`, shared as `ρ_S`
(uniform, independent of `ρ`) and `ρ_O`. For `y ≠ 0`, `t = ρy` is uniform on `Z*_n`; for `y = 0` the
owner substitutes a fresh uniform non-zero dummy, so `t` has the same distribution in both cases: the
server learns not even that `y ≠ 0`. The opening `e = ρ − u` of the product `ρ·y` is independent of `ρ`
(`u_O` fresh) and `g = y − v` of `y`, so `(e, g, t)` are independent uniform variables.

**Security argument — server confidentiality (sketch, extends Thm 26/27/30).** Write the owner's
randomness as: the cell masks `r`, per product element `(u_S, u_O, v_S, v_O, w_S)` (uniform;
`w_O = uv − w_S` is never sent), per division element `(ρ, ρ_S)` and the dummy. Every ring element the
server receives is one of: (i) a stored cell `x + r`; (ii) a fresh uniform value that is not a function
of any secret (`u_S, v_S, w_S, ρ_S`, tag shares); (iii) a *one-time-padded* share `X_O − u_O` whose pad
`u_O` (resp. `v_O`) appears in no other server-visible value (`u_O` enters only `w_O` and later
`Z_O`, which are not sent) — uniform and independent of everything earlier by Lemma 29; (iv)
`t⁻¹`, uniform on non-zero values independent of the rest as shown above; (v) public query constants.
Values the server computes (`e, g, Z_S`, its stored wires) are functions of the above. Hence the
server's view is a function of independent uniform variables and the public query, so
`I(M; V_S) = 0`, for plain and authenticated mode (tags are blinded the same way: `m̃ = αx + r_m`,
tag-triple shares uniform). Triples are never reused (a reused triple repeats `e` for equal operands —
the audit detects it). **Gap:** this is a hybrid argument, not a machine-checked proof; reviewers
should check in particular (a) that the joint independence of `(e, g, t, t⁻¹, ρ_S)` survives the
chained use of `ρ_O·t⁻¹` as an operand of the next product, and (b) that chunking a level into several
requests does not correlate triple shares.

**Integrity (authenticated mode; sketch, not a proof).** Tags are SPDZ-style with a long-lived `α`
known only to the owner (F-8), so the check is a designated-verifier one: the owner holds the whole
key. Linear gates act on value and tag alike; a public `+c` adds `α·c` to the owner's tag share; the
product's tag share is `m_w + e·m_v + g·m_u` at the server and the same plus `α·e·g` at the owner.
The owner checks (1) both openings of every product: the server's reported tag share of `e` plus the
owner's must equal `α·e` (same for `g`) — otherwise `IntegrityError`; (2) the tag of every opened
`t = ρ·y`, **before** testing it for zero (so shifting a denominator gives an `IntegrityError`, not a
zero oracle); (3) the tag of the revealed result before decoding. A server that deviates anywhere —
a stored cell, a triple or `ρ` share, the `t⁻¹` it was sent, a reported opening, a share of any wire,
the reply — shifts its (value, tag) shares by `(ε, μ)` chosen without knowledge of `α` (its view is
independent of `α`); the owner's check evaluates a polynomial in `α` of degree ≤ depth+1 whose
leading term is `α·ε`-dependent and which vanishes for a wrong value for at most that many `α`,
so a wrong result passes with probability ≤ (depth+1)·#checks / n, by Schwartz–Zippel (the algebra for
one product with a server that *reports* an honest opening but *uses* another is in
`test_a_server_that_uses_a_different_opening_than_it_reports_is_caught_at_the_end`). Open questions
for reviewers: whether the cross-layer defect propagation really stays within degree depth+1, and the
selective-failure bit (an aborted attempt eliminates one candidate `α`; F-8).

**What a malicious server can still do.** *Authenticated:* refuse service, delay, or abort; cause an
`IntegrityError` (then learn only that its guess was wrong); manipulate **plain** data — `WHERE`
results, join keys, which rows exist or are returned, row counts used by `COUNT`/`AVG` — none of
which is authenticated in either mode (F-6; the anchored FHE mode covers FHE tables only).
*Unauthenticated (`authenticated=False`, the default, F-4):* secure against a **semi-honest** server
only. A lying server can shift any wire by an amount of its choice, so the result is wrong
by a delta it knows for linear results (`test_without_authentication_a_lying_server_is_not_detected_pinned_limitation`,
`tests/test_expr_shared_e2e.py`), and by shifting a denominator's share by `−c` it learns whether
that denominator equals `c` from whether the user sees `DivisionByZero`
(`test_unauthenticated_active_attacker_gets_a_zero_oracle_authenticated_does_not`). Use
`authenticated=True` on any host that is not trusted to follow the protocol.

**Zero denominators and the abort oracle.** The runner never stops early: a zero `t` is replaced by a
random non-zero dummy and the protocol runs to its last request; `DivisionByZero` is raised after the
reveal (and after the MAC check). `test_a_zero_denominator_does_not_change_the_request_sequence`
compares the op names, wire ids, spans and vector lengths of every request with and without a zero
denominator; `test_the_opened_t_is_uniform_nonzero_and_zero_is_replaced_by_a_dummy` shows the `t⁻¹` the
server receives is uniform and indistinguishable in the two cases (χ², 2 500 samples each).

**Server state.** A session-scoped wire store (per-session caps on wires/elements, a server-wide
cap, a TTL, emptied at query end / `COMMIT` / `ROLLBACK` / transaction timeout / disconnect; every cap
violation is a named `WireError`). It holds no key, mask, MAC key or plaintext; the wire RPCs are
reads (`ro`) and never touch the database except to read the named rows. Tests: `core/tests/
test_expr_shared.py` (store caps/TTL/malformed requests, spans, cost accounting),
`tests/test_expr_shared_e2e.py` (lifecycle over TCP, roles, caps).

**The wire audit.** `core/tests/test_expr_shared.py::audit` checks everything the server receives:
the triple shares, the owner's opening shares and the `ρ` shares are χ²-uniform and never repeat;
no mask, α, encoded plaintext, intermediate, inverse or quotient appears (`expr_workload`, plain and
authenticated); every wire operation has an entry (`AUDITED_OPS`) so a new operation cannot be added
without one. The audit has teeth: a dealer that leaves the owner's triple shares at 0 (so the server
holds every product in the clear), a dealer that reuses a triple, and an owner that stores unpadded
cells are each flagged (`test_audit_has_teeth_*`).

**Where the paper and this implementation differ** (so a reviewer does not assume otherwise):

1. *Π_mult as written is owner-evaluated.* Construction 18 has the owner send `e = s − u` computed from
   the plaintext `s`, the server return `e·g`, and the owner reconstruct; Construction 20 says the
   server keeps "the running blinded wires" but never says how it obtains a blinded wire of a
   product (the reconstruction happens at the owner). Read literally, Π_C is the v0.6
   `expr_mode="owner"` evaluator. The shared-wire form implemented here is the standard completion:
   Beaver multiplication with *shared outputs*, so the product stays at the server as `Z_S`.
2. *The proofs cover less than the view.* Theorems 26/27 analyse `(e, g)` of one product; the server
   here also sees triple shares, `ρ_S`, `t⁻¹`, and many correlated phases. The argument above uses
   Lemma 29 and is a sketch.
3. *The integrity construction differs.* §IX proposes a per-wire affine tag `τ(x) = αx + β`
   with fresh `α` and says "the gates are affine/bilinear so the owner predicts the output tag". A
   product of two such tags is not a tag of the product, so that scheme does not extend to
   multiplication gates as stated; the implementation uses a single SPDZ key with MAC-checked openings
   and a final check (above).
4. *Π_boot is unnecessary.* There is no noise budget in `Z/nZ`; no bootstrap is performed. The
   rational layer `Q_E` swaps `(a,b)` pairs to invert; here one scalar `a·b⁻¹ mod n` is stored and
   division is the masked-inversion protocol above (results agree wherever both are defined).
5. *Rounds.* The paper's "δ rounds" holds; this implementation adds one request for the final reveal
   and one level per division by an encrypted value.
6. *Owner blindness.* The paper does not claim it, but a reader may infer that "delegating any
   arithmetic circuit" means the owner does not see intermediates; with an owner-dealt triple it can
   (F-22).

**Review questions (§3.3).** (a) Is the expression shape (δ, products per level, row count, request
sizes) acceptable to expose? (b) Is "continue with a dummy `t`, raise at the end" a sufficient answer to
the abort oracle? (c) Is the hybrid argument for the server's view above complete (gaps (a), (b))?
(d) Is there an acceptable triple-generation scheme that keeps the unconditional server-side
guarantee and makes the owner blind to intermediates (a second non-colluding party? OT-based with a
post-quantum OT?) — F-22. (e) Does the defect polynomial argument give the claimed bound, including
across several tampered gates? (f) Dealer reuse of `α` across sessions with an observable accept/reject
bit (F-8).

**`expr_mode="owner"` (v0.6 transport, still available).** The owner fetches the blinded operand
cells (`blinded_cells`), removes the masks, applies every gate in plaintext, deals a triple, sends
`e = x−u`, `g = y−v`; the server returns `e·g` (`mult_combine_batch`); the owner reconstructs. No
intermediate is held at the server, the owner holds every operand and intermediate in plaintext, the
server's step is vestigial (F-3, F-18). It needs no wire RPC and its server view is also uniform. It
exists for servers older than wire protocol 2.1 and as a differential oracle for the shared mode.

## 4. Integrity Protocol — SPDZ-Style MAC (§IX)

**Motivation:** Π assumes a semi-honest server (follows the protocol but may
try to infer plaintexts). For a malicious server that returns forged results,
we add an information-theoretic integrity layer.

**MAC scheme:** For each encrypted cell s, the client stores a parallel
blinded MAC column m̃ = α·s + rm where α ← Z/nZ is a secret per-session
key (owner-only) and rm is a fresh mask.

**Verification (affine results):**
For a SUM result y = Σsᵢ:
- Expected MAC: M* = α·y (mod n)
- Server computes: Σm̃ᵢ (the MAC aggregate under the protocol)
- Client unblinds and checks: M = Σm̃ᵢ − Σrmᵢ =? α·y (mod n)
- If M ≠ M*, raise IntegrityError

**Soundness:** A cheating server that returns y' ≠ y would need to also forge
M = α·y' (mod n). Since α is secret, the forgery probability is 1/n (where
n ≈ 2^254). Negligible under any realistic threat model.

**Per-row extension:** For scalar-multiply results k·sᵢ, each row is checked
independently: M_i = α·(k·sᵢ) = k·(α·sᵢ) (MAC homomorphism).

**For Π_mult:** Before each triple use, the client reads and MAC-verifies
both operands via `_read_verified_scalar`. The server's product term e·g is
also verified via the check `eg = e·g (mod n)`.

**Implementation:** `NoKeyClient._verify_mac`, `_read_verified_scalar` in
`core/torusdb_core/nokey_engine.py`.

**Activation:** `NoKeyClient(server, authenticated=True)` or
`connect(..., authenticated=True)`.

**Verification tests:** `test_integrity_*.py` — 10 tests covering:
forged SUM, forged per-row, tampered stored operand, forged product term,
unauthenticated mode misses forgery, integrity survives custody export/import.

## 5. Laurent Series Secret Sharing (LSS) — Vault Custody

**Motivation:** The mask vault (and MAC key α) is the single long-lived owner
secret. If the owner's device is lost, the data is permanently unrecoverable.
LSS provides threshold custody without weakening the server guarantee.

**Reference:** Shim & Lee, "Laurent Series Secret Sharing," J1729 Labs, 2026.

**Scheme:** 
- Secret = residue b_{-1} of a formal Laurent series f(x) = Σ bᵢ xⁱ at x=0
- The share polynomial is a Laurent series with prescribed residue b_{-1} = s
- Shares are evaluated at distinct points in Z_p (p a large prime ≈ n)
- Reconstruction: generalized-Vandermonde solve over the evaluation ring

**Properties:**
- (t, n) threshold: any t shares reconstruct; fewer than t reveal nothing
- Proactive refresh: add a fresh sharing of 0 → same secret, new shares.
  A refreshed share is uncorrelated with the pre-refresh share at the same
  point, so compromise windows are bounded by the refresh epoch.

**Verifiable custody (`VerifiableCustody`):**
Each share comes with a Pedersen-style commitment (hiding commitment).
The public Anchor contains only commitments. Recovery:
1. Requester collects t shares from custodians
2. Verifies each share against the Anchor commitment
3. Reconstructs vault key K
4. Unseals and decrypts the vault

An anti-rollback ledger (`chain.py`) chains Anchor digests — a superseded
pre-refresh Anchor is rejected.

**Implementation:** the LSS custody described here is part of the *legacy closed engine* and is NOT in this repository; it is out of scope of this packet. The open, in-repo replacement is `torussql.custody` (threshold, see `docs/custody.md`).

**Verification tests:**
- `test_lss_*.py` — 8 tests: correctness, threshold security (fewer than t
  shares cannot reconstruct), proactive refresh, epoch isolation
- `test_custody_*.py` — 7 tests: export/import quorum, share verification,
  tampered share rejected

**Review question:** The LSS residue scheme is presented as equivalent to
Shamir over a Laurent ring. The reviewers should verify:
1. That the generalized-Vandermonde matrix over the evaluation ring is
   non-singular for all valid evaluation points (the invertibility proof)
2. That the information-theoretic security of the sharing (perfect secrecy
   for < t shares) holds in the Laurent ring setting

## 9. Scope and Limitations

**In-scope for this review:**
- The one-time pad blinding argument (Construction 14)
- Π_lin (Construction 16) and its aggregate protocol
- Π_mult (Construction 18) and the Beaver triple argument
- The SPDZ MAC (§IX) soundness proof
- The LSS scheme definition and threshold security proof

**Out-of-scope:**
- Side-channel resistance (timing, memory access patterns)
- The underlying EC-FHE primitives (elliptic curve operations, BN254 pairing)
  — those are used only for the PAIRED column's ciphertext representation
  and are not involved in the no-key protocol's security argument
- Multi-party Beaver triple generation (single-owner deployment only)
- Quantum resistance of LSS polynomial reconstruction (depends on the underlying
  field; further analysis recommended)

## 10. Review Request

We request external review of the following claims, in priority order:

1. **Construction 14 (OTP):** Is the blinding argument complete? Does it hold
   for the entire aggregate (Π_lin) and not just individual cells?
   
2. **Construction 18 (Π_mult):** Does the Beaver triple argument hold when
   the triple is generated by the same party who owns the operands
   (single-owner case)?

3. **LSS Theorem (Threshold Security):** Is the generalized-Vandermonde
   construction over the Laurent ring invertible for all valid parameter choices?
   Does perfect secrecy hold for subsets of fewer than t shares?

4. **SPDZ MAC (§IX):** Is the soundness bound of 1/n tight? Are there

5. **Rational Reconstruction Bound:** Is the reconstruction domain B^2 ≪ n/4
   maintained under all aggregate operations the dialect supports (SUM of N
   rows, scaled aggregates k·SUM)?

## 12. Threshold key custody (Laurent LSS, "z-MPC style")

Full description: [`custody.md`](custody.md). Summary for reviewers.

**Sharing.** Pure-pole Laurent series over F_q: f(z)=a₀+Σ_{j=1}^{t} b_j z^{-j}, t=k−1,
secret = residue b₁, share yᵢ=f(xᵢ), xᵢ∈{1..n}, n≤32. With u=1/z this is the
polynomial g(u)=a₀+b₁u+…, secret g′(0); reconstruction from a quorum S is the linear
functional b₁=Σ λᵢyᵢ with λᵢ = −xᵢ^{k−1}(Σ_{j≠i}x_j)/Π_{j≠i}(xᵢ−x_j) (tested against
Gaussian elimination). Perfect secrecy of any k−1 shares holds iff e_{k−2}(1/x_S)≠0 mod q;
for points 1..n, n≤32 the numerator is a positive integer < q, and the property is
verified exhaustively for every (k−1)-subset in the tests (n≤10). This is perfect secrecy of the *sharing*; because Feldman commitments
publish X and every Yᵢ, secrecy of x itself is computational (ECDLP).

**DKG.** Each of n participants deals a random residue with Feldman commitments
Cₘ=cₘG and a Schnorr proof of knowledge of b₁ (context-bound to session and index);
y_j=Σᵢ sᵢ→j, X=Σᵢ Cᵢ₁. Weights w_m(x)=x^{-m} verify shares: y·G=Σ w_m(x)·Cₘ.

**Use.** Envelope: K=KDF(e·X‖E‖X‖ctx). Opening: Dᵢ=yᵢ·E with DLEQ proof
(logG Yᵢ = log_E Dᵢ), context = key_id‖epoch‖request context; combine Σλᵢ Dᵢ.

**Reshare.** Quorum S deals Laurent sharings of λᵢyᵢ to a new committee; check
C′ᵢ₁=λᵢ·Yᵢ, per-share commitments, and that the aggregated public key is unchanged.

**Review questions.** (1) Is the Laurent-in-reciprocal construction (secret = g′(0))
sound for the stated point sets, in particular the perfect-secrecy argument? (2) Is
Feldman+PoK acceptable for a one-time custody ceremony, or should the Pedersen
(GJKR) variant be required? (3) Is binding the DLEQ context to (key_id, epoch,
request context) sufficient against cross-protocol reuse? (4) Is ECDLP-based custody an
acceptable replacement for information-theoretic custody given F-13, or should a
hybrid be offered? (5) The opener learns K for the envelope; is that acceptable?
